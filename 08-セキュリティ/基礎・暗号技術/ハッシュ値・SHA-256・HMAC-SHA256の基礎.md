## 1. ビットとバイト

コンピューターは、データを `0` と `1` の組み合わせで扱う。

### 1.1. ビット（bit）

ビットは、コンピューターが扱う情報の最小単位。

- `0` または `1` を表現する。
- 小文字の `b` で表記する。

### 1.2. バイト（Byte）

バイトは8ビットをまとめた単位。

- **1 B = 8 b**
- 大文字の `B` で表記する。


| ビット   | バイト  |
| ----- | ---- |
| 8 b   | 1 B  |
| 16 b  | 2 B  |
| 32 b  | 4 B  |
| 256 b | 32 B |

## 2. UTF-8と文字のデータ表現

UTF-8とは、文字をコンピューターが扱えるバイト列に変換するための文字エンコーディング方式。

コンピューターは文字そのものではなく、ビット列としてデータを扱う。

### 2.1. 文字とバイト数の関係


| 文字  | UTF-8の2進数                    | サイズ |
| --- | ---------------------------- | --- |
| `h` | `01101000`                   | 1 B |
| `A` | `01000001`                   | 1 B |
| `あ` | `11100011 10000001 10000010` | 3 B |


UTF-8では文字によって必要なバイト数が異なる。

### 2.2. 具体例

英字の `hello` は5文字なので、UTF-8では5バイトとなる。

```
hello
  ↓ UTF-8
5 B = 40 b
```

一方、`hello1` は6バイトとなる。

```
hello1
  ↓ UTF-8
6 B = 48 b
```

**ポイント：文字数とバイト数は必ずしも一致しない。**

## 3. ハッシュ値の概要

ハッシュ値とは、元のデータをハッシュ関数によって計算した結果のこと。

ハッシュ関数の代表例として、SHA-256がある。

```
元のデータ
    ↓
ハッシュ関数
    ↓
ハッシュ値
```

### 3.1. ハッシュ値の特徴


| 特徴       | 説明                         |
| -------- | -------------------------- |
| 再現性      | 同じ入力なら必ず同じハッシュ値になる         |
| 固定長      | SHA-256などは出力サイズが一定         |
| 一方向性     | 元の値への復元は現実的に困難             |
| アバランシェ効果 | 入力の小さな変化が出力全体に広がる          |
| 衝突       | 異なる入力から同じハッシュ値が生成される可能性がある |


### 3.2. 同じ入力なら同じハッシュ値になる

```
1回目
hello → SHA-256 → ハッシュ値A

2回目
hello → SHA-256 → ハッシュ値B

結果：A = B
```

SHA-256はランダムに値を生成するのではなく、決められたルールで計算する。

そのため、同じ入力であれば必ず同じハッシュ値になる。

ただし、異なる入力でも同じハッシュ値になる「衝突」の可能性は理論上存在する。

## 4. SHA-256の仕組み

SHAとは、**Secure Hash Algorithm** の略。

SHA-256は、入力データから256ビットのハッシュ値を生成するアルゴリズム。

### 4.1. 出力サイズ

SHA-256の出力は必ず256ビットとなる。

**256 b ÷ 8 = 32 B**

入力データがどれだけ長くても、ハッシュ値のサイズは変わらない。


| 入力データ      | 入力サイズ   | 出力サイズ |
| ---------- | ------- | ----- |
| `hello`    | 40 b    | 256 b |
| `hello1`   | 48 b    | 256 b |
| 英数字100文字   | 800 b   | 256 b |
| 英数字1,000文字 | 8,000 b | 256 b |


※ UTF-8で表現した場合。

### 4.2. なぜ16進数では64文字になるのか

16進数では、4ビットを1文字で表現できる。

そのため、

**256 b ÷ 4 b = 64文字**

となる。


| 表現方法 | ハッシュ値の長さ |
| ---- | -------- |
| 2進数  | 256桁     |
| バイト  | 32 B     |
| 16進数 | 64文字     |


例えば、`hello` のSHA-256ハッシュ値は次のとおり。

```
2cf24dba5fb0a30e26e83b2ac5b9e29e
1b161e5c1fa7425e73043362938b9824
```

これは16進数の64文字で表現されている。

**重要：ハッシュ値そのものは256ビットであり、64文字というのは16進数で表示した場合の長さである。**

### 4.3. SHA-256の内部処理

SHA-256は次の手順でハッシュ値を生成する。

1. 入力データをビット列として扱う。
2. パディングという決められたルールでデータを補う。
3. 512ビット単位のブロックに分割する。
4. 各ブロックを順番に計算し、内部状態を更新する。
5. 最終的に256ビットのハッシュ値を出力する。

```
入力データ
    ↓
パディング
    ↓
512ビット単位に分割
    ↓
各ブロックを順番に計算
    ↓
256ビットのハッシュ値
```

SHA-256は内部で32ビットの値を8個管理している。

```
32 b × 8 = 256 b
```

最終的には、これら8個の値を連結して256ビットのハッシュ値を生成する。

### 4.4. なぜ1文字違うだけで結果が変わるのか

例えば、次の文字列を比較する。

```
hello
hello1
```

違いは末尾の `1` が追加されていることだけ。

しかし、SHA-256ではビット演算や加算などを繰り返すため、小さな違いが出力全体に広がる。

これを**アバランシェ効果**と呼ぶ。

そのため、`hello` と `hello1` では大きく異なるハッシュ値が生成される。

## 5. ハッシュ化・暗号化・マスキングの違い


| 技術    | 目的             | 元の値への復元     |
| ----- | -------------- | ----------- |
| ハッシュ化 | データの一致・整合性確認など | 原則できない      |
| 暗号化   | データを秘匿する       | 正しい鍵があればできる |
| マスキング | データを見えないようにする  | 方式による       |


### 5.1. ハッシュ化

```
hello
  ↓ SHA-256
ハッシュ値
  ↓
元の値には復元できない
```

### 5.2. 暗号化

```
hello
  ↓ 暗号化
暗号文
  ↓ 正しい鍵で復号
hello
```

### 5.3. マスキング

```
元の値：password123
表示値：***********
```

画面表示だけをマスキングする場合、内部には元の値が保持されている。

※ 元データ自体を置換・削除するマスキング方式もある。

## 6. ハッシュ値の主な用途

### 6.1. データの整合性確認

ファイルなどのデータが変更されていないかを確認するために利用できる。

```
元のファイル
    ↓ SHA-256
ハッシュ値A

受信したファイル
    ↓ SHA-256
ハッシュ値B

AとBを比較
    ↓
一致 → 同じデータである可能性が非常に高い
```

ただし、元のハッシュ値自体が信頼できることが前提となる。

### 6.2. パスワードの一致確認

パスワードを平文のままDBに保存せず、一致確認するためにもハッシュ化を利用する。

ただし、実際のパスワード管理ではSHA-256単体ではなく、**Argon2idなどのパスワード専用ハッシュ関数**を使用する。

理由は、SHA-256は計算が高速で、攻撃者が大量のパスワード候補を試しやすいため。

Argon2idではソルトを使用し、計算コストも高める。そのため、単純なハッシュ値の直接比較ではなく、専用の検証処理を行う。

## 7. HMAC-SHA256の仕組み

HMACは、**Hash-based Message Authentication Code** の略。

HMAC-SHA256は、SHA-256を利用し、入力データと秘密鍵から認証用の値（署名）を生成する仕組み。

### 7.1. SHA-256との違い

**SHA-256**

```
入力データ
    ↓
  SHA-256
    ↓
 ハッシュ値
```

入力データを知っていれば、誰でも同じハッシュ値を計算できる。

**HMAC-SHA256**

```
入力データ ＋ 秘密鍵
         ↓
     HMAC-SHA256
         ↓
        署名
```

正しい署名を生成するには秘密鍵が必要となる。

※ HMACは単純にデータと秘密鍵を連結するのではなく、秘密鍵を組み込んだ専用の計算方式を使用する。

### 7.2. なぜSHA-256だけでは改ざんを防げないのか

例えば、Cookieに次の情報が保存されていたとする。

```
セッションID = abc123
ハッシュ値 = SHA-256(abc123)
```

攻撃者がセッションIDを変更する。

```
abc123 → xyz999
```

SHA-256では秘密鍵が不要なため、攻撃者自身が変更後のセッションIDからハッシュ値を計算できる。

```
攻撃者：
SHA-256(xyz999) を計算

サーバー：
SHA-256(xyz999) を計算

結果：一致する
```

つまり、通常のSHA-256だけでは、改ざんしたデータに対応するハッシュ値を攻撃者が作成できてしまう。

### 7.3. HMAC-SHA256による改ざん防止

HMAC-SHA256では秘密鍵を使用する。

```
セッションID = abc123
秘密鍵 = SESSION_SECRET

HMAC-SHA256(abc123, SESSION_SECRET)
          ↓
         署名
```

`SESSION_SECRET` はAPIサーバーだけが知っている秘密鍵とする。

攻撃者がセッションIDを変更しても、秘密鍵を知らなければ正しい署名を生成できない。

```
攻撃者：
セッションIDを xyz999 に変更
秘密鍵を知らない
    ↓
正しい署名を生成できない

サーバー：
HMAC-SHA256(xyz999, SESSION_SECRET)
    ↓
署名を再計算
    ↓
受信した署名と比較
    ↓
不一致 → 署名検証失敗
```

これにより、改ざんを検知できる。

## 8. Cookieにおける署名検証

### 8.1. Cookieの構造

例えば、署名付きCookieは次の形式になる。

```
connect.sid=s:<セッションID>.<署名>
```


| 項目              | 役割               |
| --------------- | ---------------- |
| セッションID         | セッションを識別する       |
| 署名              | セッションIDの改ざんを検証する |
| SESSION\_SECRET | 正しい署名を生成・検証する秘密鍵 |
| Base64          | 署名を文字列として表現する    |


HMAC-SHA256の出力は256ビットのバイナリデータであり、Base64で文字列に変換してCookieへ格納できる。

※ 実際にはBase64のパディングを省略する実装もある。

### 8.2. Cookieの検証フロー

```
flowchart TD
    A["ブラウザからCookieを送信"] --> B["APIサーバー"]
    B --> C["セッションIDと署名を取得"]
    C --> D["秘密鍵を使って署名を再計算"]
    D --> E{"署名が一致するか？"}
    E -->|No| F["署名検証失敗"]
    E -->|Yes| G["Redisからセッションを取得"]
    G --> H{"有効なセッションか？"}
    H -->|Yes| I["ログイン状態として扱う"]
    H -->|No| J["認証失敗"]
```

署名の検証とセッションの有効性確認は、別々の役割を持つ。

- **HMAC-SHA256**：Cookieの改ざんを検証する。
- **Redis**：セッションIDに対応するセッション情報が有効か確認する。

### 8.3. セキュリティ上の注意点


| 漏洩した情報     | 想定されるリスク                    |
| ---------- | --------------------------- |
| セッションIDのみ  | 正しい署名を作れなければ基本的になりすませない     |
| セッションID＋署名 | 有効なCookieを再利用される可能性がある      |
| 秘密鍵のみ      | 有効なセッションIDも分かれば、正しい署名を生成できる |


HMAC-SHA256は、**Cookieの改ざんを検証する仕組みであり、Cookieの盗難そのものを防ぐ仕組みではない。**

そのため、HTTPSやCookieの `HttpOnly`・`Secure` 属性、セッションの有効期限管理なども必要となる。

### 8.4. 最終まとめ


| 技術          | 役割                   |
| ----------- | -------------------- |
| bit・Byte    | データ量の単位              |
| UTF-8       | 文字をバイト列に変換する         |
| SHA-256     | 256ビットのハッシュ値を生成する    |
| HMAC-SHA256 | 秘密鍵を利用して署名を生成・検証する   |
| Base64      | バイナリデータを文字列として表現する   |
| Cookie      | セッションIDと署名をブラウザに保持する |
| Redis       | セッション情報の保存・有効性管理を行う  |


**SHA-256はデータからハッシュ値を生成する技術。HMAC-SHA256は、秘密鍵を組み合わせることでデータの改ざん検証を可能にする技術である。**
