### 2026-08-17：スプリント計画の共有不足


| 観点      | 内容                                                                                                                        |
| ------- | ------------------------------------------------------------------------------------------------------------------------- |
| 起きたこと   | PLを中心に計画が決められ、チーム全員でスプリントの目標、作業内容、優先順位を議論する機会が十分に設けられていなかった                                                               |
| 問題・影響   | 計画の背景や全体像が十分に共有されないため、メンバーが現在の状況や進捗を把握しにくく、PLへの支援や問題の早期発見が難しい。計画への関与が少ない状態が続くと、当事者意識や自律性が育ちにくくなり、中長期的には開発速度や品質へ影響する可能性がある |
| 原因      | プランニングを、チームで実現可能性を確認して共通認識を形成する場ではなく、PLが決めた計画を展開する場として進めていた。計画の決定過程にメンバーが参加する目的や、共有すべき情報が明確になっていなかった                      |
| 改善策     | スプリント開始前に、チーム全員が目標、優先順位、作業内容、懸念点を説明できる状態にする。プランニングでは計画の決定理由と変更点を記録し、最後に各メンバーの疑問点、懸念点、支援が必要な事項を確認する                        |
| 次のアクション | 次回のプランニングで、チーム全員が計画について意見を出せる進め方を提案し、確認項目をチームで合意する                                                                        |


### 2026-08-18：PRレビューのPLへの集中


| 観点      | 内容                                                                                                                                            |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 起きたこと   | PRレビューを主にPLが担当していたため、PL自身のタスクが停滞し、ほかのチームメンバーがレビューに参加する機会も限られていた                                                                                |
| 問題・影響   | ① レビュー待ちやPL自身のタスクの停滞が発生し、PLが開発のボトルネックになりやすい　② レビューの観点や実装に関するナレッジがPLに偏る　③ チーム内の知識と品質基準が均一になりにくく、チーム全体での品質向上が難しくなる　④ メンバーが品質に責任を持つ機会が減り、当事者意識が育ちにくくなる |
| 原因      | PL以外のメンバーがレビューできるようになることをチームの育成目標として定めておらず、レビュー観点の共有や、メンバーが段階的にレビュー経験を積む仕組みが不足していた                                                            |
| 改善策     | PRレビューを特定の役割に固定せず、チームメンバーが相互に担当できる運用へ段階的に移行する。レビュー観点と判断基準をチェックリストやコメント例として共有し、必要に応じてPLがレビュー結果を補完する。最終的には、PLだけでなく各メンバーが品質を判断し、レビューを完結できる状態を目指す |
| 次のアクション | 次回のPRからメンバーをレビュアーに割り当て、PLと共同でレビューする。レビュー後に判断に迷った点を共有し、チーム共通のレビュー観点として蓄積する                                                                     |

#### 具体的にやるべきこと

- チケットの完了条件を満たしているか確認する
- 要件や業務ルールと相違していないか確認する
- テストコードで条件分岐を適切に網羅しているか確認する
- ローカル環境で実際に動作させて確認する
- レビュアーが確認できるように、動作確認の手順をPRコメントへ記載する


### 2026-08-19：業務ルールの正本が不明確


| 観点      | 内容 |
| ------- | --- |
| 起きたこと   | 実装を開始しているが、どの資料を正本として業務ルールや仕様を整理したのか分からない状態になっていた |
| 問題・影響   | 後から仕様を見返したときに、その内容が正しいか判断できない。資料ごとに記載が異なっても優先すべき情報を選べず、誤った実装や確認の手戻りにつながる可能性がある |
| 原因      | 業務ルールを記載する場所と正本を明確に決めず、情報源、決定理由、更新履歴、関連資料との関係を残していなかった |
| 改善策     | 業務ルールを一元管理する正本を決め、ルールごとに内容、適用条件、例外、根拠、決定者、更新日を記載する。チケットや設計資料には内容を重複して書かず、正本へのリンクを記載する |
| 次のアクション | 現在の実装に関係する業務ルールと資料を洗い出し、どの資料を正本とするかチームで合意する。不明な仕様は関係者へ確認し、判断結果と根拠を正本へ反映してから実装との差異を確認する |
