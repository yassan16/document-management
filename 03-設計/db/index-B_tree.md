# DBインデックスとB-treeの基礎

## 1. インデックスとは

インデックスは、テーブルから目的のデータを高速に探すための**検索用データ構造**です。

例えば次のようなテーブルがあるとします。

```sql
CREATE TABLE users (
    id   INT,
    name VARCHAR(100),
    age  INT
);

```

`age` にインデックスを作成する場合は、次のようにします。

```sql
CREATE INDEX idx_users_age
ON users(age);

```

このとき、`users` テーブルとは別に、`age` の値を検索するためのインデックス構造が作られます。

```text
usersテーブル
   │
   └── 実データ

ageインデックス
   │
   └── ageを高速に探すための構造

```

DBで一般的に利用されるインデックスの代表例が、B-tree系のインデックスです。

---

# 2. B-treeの全体構造

B-treeは、データを木構造で管理します。

大きく次の3種類のノードがあります。

```text
                 Rootノード
                     │
                     ↓
                 中間ノード
                     │
                     ↓
                 Leafノード

```

それぞれの役割は次の通りです。


| 種類      | 役割                 |
| ------- | ------------------ |
| Rootノード | 検索の開始地点            |
| 中間ノード   | 検索範囲をさらに絞る         |
| Leafノード | 最終的なキーと行を特定する情報を持つ |


Rootも中間ノードもLeafも、すべて「ノード」の一種です。

Rootだけが複数存在するわけではなく、基本的にRootは1つです。

---

# 3. B-treeは二分木ではない

B-treeでは、1つのノードから複数の子ノードへ分岐できます。

例えばRootが次のようになっているとします。

### 例1

```text
              Root
        [ 30 | 60 | 90 ]
          /    |    |    \
         ↓     ↓    ↓     ↓
       <30   30-59 60-89  >=90

```

`30`、`60`、`90`という複数のキーを持つことで、4方向に分岐できます。

例えば `75` を検索した場合は、

```text
75
 ↓
[ 30 | 60 | 90 ]
          ↓
     60〜89の範囲

```

へ進みます。

### 例2

Rootがさらに多くのキーを持つ場合もあります。

```text
                 Root
       [ 20 | 40 | 60 | 80 ]
         /    |    |    |    \
        ↓     ↓    ↓    ↓     ↓
      <20   20-39 40-59 60-79 >=80

```

この場合は5方向に分岐できます。

例えば `53` を検索した場合は、

```text
53
 ↓
[ 20 | 40 | 60 | 80 ]
          ↓
       40〜59

```

の子ノードへ進みます。

つまり、Rootが持つキーの数によって分岐数も変わります。

そのため、

```text
B-tree = 半分ずつ2方向に分割する木

```

ではありません。

正しくは、

```text
1つのノードに複数のキーを持ち、
複数の子ノードへ分岐する木

```

です。

---

# 4. ノードには何が入っているのか

Rootノードや中間ノードは、主に次の2つを持ちます。

- 検索の基準となるキー
- 子ノードへのポインタ

概念的には次のような構造です。

```text
┌────────────────────────────────────┐
│ ptrA │ 30 │ ptrB │ 60 │ ptrC      │
└────────────────────────────────────┘
   │           │             │
   ↓           ↓             ↓
  <30       30〜59          >=60

```

つまり、

```text
ポインタ
   ↓
キー
   ↓
ポインタ
   ↓
キー
   ↓
ポインタ

```

という関係になっています。

---

# 5. 実際にどのように検索するのか

`age` にインデックスがあり、次のSQLを実行するとします。

```sql
SELECT *
FROM users
WHERE age = 47;

```

B-treeが次のような構造だったとします。

```text
Root
[30 | 60]
     │
     │ 30 < 47 < 60
     ↓

中間ノード
[40 | 50]
     │
     │ 40 < 47 < 50
     ↓

Leafノード
[41, 45, 47, 49]
         ↑
        発見

```

検索の流れは次の通りです。

```text
47を検索
   ↓
Rootで範囲を判断
   ↓
該当する中間ノードへ進む
   ↓
さらに範囲を絞る
   ↓
Leafノードへ到達
   ↓
47を発見
   ↓
対応する実データを取得

```

テーブル全体を先頭から探すのではなく、必要な範囲だけをたどれます。

---

# 6. Leafノードには何が入っているのか

Leafノードには、実際のインデックスキーと、目的の行を特定するための情報などが格納されます。

例えば概念的には、

```text
Leafノード

┌────────────────────┐
│ 40 → rowA          │
│ 42 → rowB          │
│ 45 → rowC          │
│ 48 → rowD          │
└────────────────────┘

```

のような構造です。

`age = 45` が見つかれば、

```text
45
 ↓
rowC
 ↓
usersテーブルの該当行

```

というように実データへアクセスします。

Leafノードも、1つの値だけを持つわけではありません。

```text
Leaf
[40 | 42 | 45 | 48 | ...]

```

のように複数のキーを保持します。

なお、Leafに具体的に何を保持するかは、DBMSやインデックスの種類によって異なります。

---

# 7. なぜB-treeは安定して検索できるのか

B-treeは**平衡木（Balanced Tree）**です。

つまり、どのLeafノードもRootからの距離が同じになるように維持されます。

```text
              Root
            /      \
           ↓        ↓
         Node      Node
        /   \      /   \
       ↓     ↓    ↓     ↓
     Leaf  Leaf  Leaf  Leaf

```

どのデータを探しても、

```text
Root
 ↓
Node
 ↓
Leaf

```

というほぼ同じ階層を通ります。

そのため、

```text
小さい値だから速い
大きい値だから遅い

```

といった極端な差が起こりにくく、安定した探索性能を得られます。

---

# 8. なぜ1ノードに複数のキーを持つのか

二分木では、1ノードから最大2方向にしか進めません。

```text
        [50]
       /    \
      ↓      ↓

```

一方、B-treeでは、

```text
[20 | 40 | 60 | 80]
 /    |    |    |    \
↓     ↓    ↓    ↓     ↓

```

のように一度に多数の範囲へ分けられます。

そのため、

```text
大量のデータ
      ↓
少ない階層で絞り込める
      ↓
ディスクアクセスを減らせる

```

というメリットがあります。

---

# 9. 数値カラムのインデックス

例えば、

```text
10
20
30
40
50
60

```

という値であれば、数値の大小関係を使って順番に管理します。

```text
10 < 20 < 30 < 40 < 50 < 60

```

そのため、

```sql
WHERE age = 40

```

だけでなく、

```sql
WHERE age > 40

```

や、

```sql
WHERE age BETWEEN 30 AND 50

```

といった範囲検索にもB-treeは向いています。

---

# 10. 文字列カラムのインデックス

文字列の場合も基本的な仕組みは同じです。

例えば、

```sql
CREATE INDEX idx_users_name
ON users(name);

```

とします。

データが、

```text
Alice
Bob
Carol
David
Mike
Tom

```

なら、文字列の比較ルールに従って順序付けされます。

```text
              Root
          [ Carol | Mike ]
            /      |      \
           ↓       ↓       ↓
      Alice,Bob  David    Tom

```

例えば、

```sql
WHERE name = 'David'

```

なら、

```text
David > Carol
David < Mike

```

なので、その間に対応するノードへ進みます。

文字列の並び順は、DBの**照合順序（Collation）**によって決まります。

そのため、次のような扱いは設定によって異なる場合があります。

- 大文字と小文字
- 日本語
- アクセント付き文字
- 言語ごとの並び順

---

# 11. インデックスが効きやすい検索

B-treeは、検索範囲を大きく絞れる条件で効果を発揮します。

例えば、

```sql
WHERE id = 100

```

なら、

```text
大量のデータ
   ↓
B-treeで探索
   ↓
ほぼ1件

```

まで絞れます。

また、

```sql
WHERE id > 100

```

のような範囲検索も、値が順序付けされているため効率よく検索できます。

---

# 12. 否定条件では効果が小さくなりやすい

例えば、

```sql
WHERE id != 100

```

とすると、

```text
1       対象
2       対象
...
100     対象外
101     対象
...

```

となり、ほとんどの行が対象になります。

100万件のうち、

```text
id = 100

→ 1件程度

```

ならインデックスによる絞り込み効果は非常に大きいですが、

```text
id != 100

→ 999,999件程度

```

では、ほぼすべてのデータを取得する必要があります。

そのためDBMSが、

```text
インデックスをたどるより
テーブル全体を読んだ方が速い

```

と判断し、フルテーブルスキャンを選択することがあります。

ただし、

```sql
!=
<>

```

を使ったら必ずインデックスが使われないわけではありません。

対象件数やデータ分布、DBMSの統計情報などを元に、オプティマイザが判断します。

---

# 13. インデックス対象カラムは「裸」で使う

例えば `col_1` にインデックスがあるとします。

```sql
CREATE INDEX idx_col1
ON SomeTable(col_1);

```

B-treeに保持されているのは、基本的に `col_1` の値です。

```text
50
70
80
90
100
110
120

```

そのため、

```sql
WHERE col_1 > 100

```

であれば、そのままB-treeの値を使って検索できます。

---

# 14. カラムに演算するとインデックスを使いにくくなる

例えば、

```sql
WHERE col_1 * 1.1 > 100

```

とすると、検索対象は、

```text
col_1

```

ではなく、

```text
col_1 * 1.1

```

になります。

しかし通常のインデックスが保持しているのは、

```text
col_1

```

の値です。

そのため、通常のB-treeインデックスでは直接検索しにくくなります。

インデックスを利用できなければ、概念的には、

```text
1行読む
 ↓
col_1 × 1.1
 ↓
100より大きいか判定
 ↓
次の行

```

を繰り返すことになり、フルテーブルスキャンになる可能性があります。

---

# 15. 式変形してカラムを裸にする

例えば、

```sql
WHERE col_1 * 1.1 > 100

```

は、

```sql
WHERE col_1 > 100 / 1.1

```

と変形できます。

すると、

```text
100 / 1.1 ≒ 90.91

```

なので、

```sql
WHERE col_1 > 90.91

```

という通常の範囲検索として扱えます。

B-treeから、

```text
50  70  80  90  100  110  120
                  ↑
              この辺から

```

と開始位置を探せるため、インデックスを利用しやすくなります。

重要なのは、

```text
計算そのものが遅い

```

ことではありません。

本質は、

```text
カラムを加工する
   ↓
B-treeのキーを直接使って
検索開始位置を決めにくくなる
   ↓
大量の行を確認する必要が出る

```

という点です。

---

# 16. 関数でも同じ

例えば `name` にインデックスがある場合、

```sql
WHERE name = 'Tanaka'

```

なら通常のインデックスを利用しやすいです。

一方、

```sql
WHERE UPPER(name) = 'TANAKA'

```

とすると、

```text
name

```

ではなく、

```text
UPPER(name)

```

が検索対象になります。

通常の `name` インデックスには `UPPER(name)` の結果が保存されているわけではないため、インデックスを直接利用しにくくなります。

ただしDBMSによっては、

- 式インデックス
- Function-based Index
- オプティマイザによる式変形

などを利用できる場合があります。

そのため、

```text
関数・演算を使う
= 必ずインデックスが使われない

```

ではなく、

```text
通常のB-treeインデックスを
利用しにくくなる

```

と理解するのが正確です。

---

# 17. 文字列検索とLIKE

文字列も順番に並んでいるため、

```sql
WHERE name LIKE 'Tan%'

```

のような前方一致は、DBMSや照合順序などの条件によってはB-treeを利用できます。

```text
Tanaka
Taniguchi
Taniyama

```

のように、同じ接頭辞を持つ文字列が近くに並ぶためです。

一方、

```sql
WHERE name LIKE '%naka'

```

では先頭部分が分かりません。

そのため、

```text
B-treeのどこから探せばいいか

```

を決めにくく、通常のB-treeインデックスは効きにくくなります。

---

# 18. まとめ

B-treeインデックスの基本的な考え方は次の通りです。

```text
インデックス対象カラム
        ↓
値を順序付けして管理
        ↓
      Root
        ↓
    中間ノード
        ↓
      Leaf
        ↓
   対象行を特定

```

重要なポイントは次の通りです。

- B-treeは木構造の検索用データ構造
- Rootは基本的に1つ
- 1つのノードには複数のキーが入る
- 1つのノードから複数方向へ分岐できる
- Root・中間ノードはキーと子ノードへのポインタを持つ
- Leafには実際のキーと行を特定する情報などが格納される
- B-treeは平衡木なので、どの値でもRootからLeafまでの距離がほぼ同じ
- 数値でも文字列でも、値の順序を利用して検索する
- `=` や範囲検索では効果を発揮しやすい
- `!=` など大量の行が対象になる条件では効果が小さくなりやすい
- インデックス対象カラムは可能な限りそのまま検索条件に使う
- カラムに関数や演算を適用すると、通常のインデックスを利用しにくくなる

特に重要なのは、

> **B-treeインデックスとは、「検索対象カラムの値を順序付けし、RootからLeafまで範囲を段階的に絞り込むことで、テーブル全体を読まずに目的のデータを見つける仕組み」である。**

という理解です。
